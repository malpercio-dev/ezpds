#### State Machine &amp; Types

The migration uses an **implicit state machine** rather than an explicit enum. The orchestrator drives three sequential operations:

1. **Path Detection** → `detect_migration_path_cmd`
2. **Build + Sign** → `build_migration_op_cmd` (parks signed op in `MigrationState`)
3. **Submit** → `submit_migration_op_cmd` (consumes the parked op)

#### The Five Transfer Legs (Operation Ordering)

The migration performs **atomic repointing** of a single PLC operation. It is NOT a multi-leg process but a **single operation** that changes:

1. **rotationKeys**: Device key preserved at `[0]`, recommended keys from destination at `[1+]`
2. **services.atproto_pds**: Changed to destination's endpoint
3. **verificationMethods.atproto**: Changed to destination's verification method
4. **alsoKnownAs**: **Preserved** (critical invariant)

**Partial Failure Representation:**

The migration doesn't track partial progress — it either succeeds entirely or fails. Resumability is NOT built in; the orchestrator retries from scratch if `submit_migration_op_cmd` fails.

#### Biometric Approval Gate

**Location:** The frontend, NOT the Rust backend.

**Flow:**
1. `buildMigrationOp()` IPC call → returns `SignedMigrationOp` with `diff` and `signed_op`
2. Frontend displays the diff to the user (ReivewOperationScreen-like UI)
3. User confirms with biometric (TouchID/FaceID) — this is a **native OS gesture**, not a Tauri command
4. `submitMigrationOp()` IPC call with the signed op already in `MigrationState`

**Why not in Rust:** The device key never leaves the Secure Enclave, and signing is deterministic (RFC 6979). Biometric approval is a **policy gate** (block user action after review), not a **cryptographic gate** (cannot be cryptographically enforced by the backend). Doing it in the frontend lets the user see the proposed changes before committing biometrically.
