<title>Create flow: approve OAuth consent in-wallet, without a browser takeover or password prompt</title>
<description>
Extends <issue id="9cfb3005-9011-4b73-bf18-43ecacfd64ce" href="https://linear.app/malpercio/issue/MM-441/wallet-confirmed-oauth-consent-phase-a-pending-authorization-primitive">MM-441</issue>/<issue id="16b372c8-06fa-4a9b-b6c7-239e5b4455e9" href="https://linear.app/malpercio/issue/MM-442/wallet-confirmed-oauth-consent-phase-b-qr-scan-on-the-consent-page">MM-442</issue> (wallet-confirmed OAuth consent) and resolves the open question left in `docs/design-plans/2026-07-18-wallet-confirmed-oauth-consent.md`:

> **Does the wallet-path consent page still render the password form?** Proposal: render the password form only for accounts that have one (requires the identifier first...)

## Observed

At the end of account creation the wallet advances to `authenticating`, which calls `startOAuthFlow(handle)` (`AuthenticatingScreen.svelte`) and opens the authorize page as a full-screen takeover over the app. The page offers two paths, and for a freshly created passwordless account **neither is reachable**:

* **Password form** — the account has no password.
* **Wallet path** — the instructions are "scan this with Obsign on your phone" and "open Obsign and enter this code". Both assume the browser is somewhere other than Obsign. Here the browser is a modal owned by Obsign, so the handoff points at the app hosting it, and dismissing the modal cancels the OAuth flow.

Signup therefore cannot complete on a passwordless account. This is the gate on shipping `accounts.password_optional` to a public beta.

## Why the obvious fix is unsafe

Hiding the password form for accounts that lack one requires knowing the account at render time. It isn't known: `oauth_authorize.rs` (~line 485) deliberately leaves `account_did` NULL because the client-supplied `login_hint` is unverified. Branching the rendered page on whether an account has a password makes `GET /oauth/authorize` an unauthenticated account-existence and credential-shape oracle — the property `delete_account.rs:37` explicitly preserves elsewhere. The design plan's "requires the identifier first" parenthetical is this problem, unsolved.

## Proposed shape

Two independent changes; the first is the fix, the second is general polish.

### 1. Same-device, no-browser consent for wallet-initiated authorization (the fix)

The wallet has just authored the genesis op with the device key and holds a fresh session — round-tripping through a web consent page to prove an identity it demonstrably possesses is ceremony with no security value, and the takeover makes it unreachable regardless.

The approval machinery already exists: `preview_oauth_consent_by_request_id` and `confirm_oauth_consent` (`apps/identity-wallet/src-tauri/src/oauth_consent.rs`). The only gap is that `request_id` is minted as a side effect of rendering HTML (`create_pending_request`, called from the `GET /oauth/authorize` handler).

* Add a JSON affordance so a wallet-native client can create the pending authorization directly and receive `{request_id, user_code}` without rendering a consent page.
* Create flow then runs entirely in-process: mint request → preview → biometric gate → sign envelope → confirm → complete → receive the authorization code. No web view, no takeover, no password form.
* The identity is already registered in IdentityStore before this point (`finishCreateFlow` → `registerCreatedIdentity`, `apps/identity-wallet/src/routes/+page.svelte:543`, ahead of `step = 'complete'`), so the wallet has a signable identity to approve with.

**Check first:** what the post-create OAuth is actually for. `perform_did_ceremony` already persists a session token to the Keychain. If that session covers what the app does next, the create flow may not need an OAuth round trip at all and this collapses to deleting a step.

### 2. Client-declared wallet-native rendering (general)

For wallet-initiated authorizations that *do* render a page, let the wallet's canonical OAuth client (`identitywallet.obsign.org`) signal that only the wallet path should be rendered. Keying off `client_id` reveals nothing about any account — the client declares its own capability — so it carries none of the oracle risk of keying off `login_hint`.

## Acceptance criteria

* A passwordless account created in the wallet reaches the home screen without a browser takeover and without ever being shown a password field.
* No consent-page rendering decision depends on `login_hint` or on whether a given account has a password; `GET /oauth/authorize` remains non-enumerable.
* The in-process approval reuses the existing signed-envelope verification (binding `request_id`, `client_id`, granted-scope hash) — no second, weaker approval path.
* Scope reduction stays available on the in-wallet path.
* Cross-device and typed-code paths are unchanged and still work for third-party clients.
* Drivable end to end in the browser harness (`VITE_HARNESS=fake`), including the passwordless create path.

<title>Passwordless auth: retire the account password in favor of device-key/passkey factors</title>
<description>
Follow-up to the passwordless design exploration captured in `docs/design-plans/2026-07-12-passwordless-auth.md` (branch `claude/passwordless-login-bc4umw`).

## Why

The password is already a second-class credential in this architecture: the wallet logs in via OAuth+DPoP and retains no password, the root of trust is the Secure-Enclave device key holding `rotationKeys[0]`, `accounts.password_hash` has been nullable since V008, and `createSession` already falls through to app-password verification for accounts with a NULL main password. Meanwhile password reset is dead in practice (outbound email is stubbed, <issue id="fbeb902e-c32b-400a-af47-37eccd58d65b" href="https://linear.app/malpercio/issue/MM-211/outbound-email-delivery-email-confirmationupdate-endpoints">MM-211</issue>), so the password is an unrecoverable liability posing as a recovery factor. Identity recovery never depended on it — that's the device key's 2-of-3 Shamir split.

## What the password still gates (the actual work)

1. **OAuth consent** (`oauth_authorize.rs`) — the wallet's own login path; a NULL-hash account cannot pass consent today. Needs a device-key-signed or passkey (WebAuthn) factor. The signed-envelope verification pattern already exists for admin-companion devices (`auth/guards.rs::verify_admin_device_request`).
2. **Account creation** — non-empty password required in `/v1/dids` and `createAccount` new-account mode; make optional (migration mode already stores NULL).
3. `deleteAccount` — password + email token in body; rework to email-token-or-wallet-signature for passwordless accounts.
4. Third-party clients (Bluesky app, goat) keep working via **app passwords** minted in the wallet — zero server changes needed.

## Phasing (from the design plan)

* **Phase 1:** optional password at creation; device-key/passkey factor on OAuth consent; `deleteAccount` rework. Keep interop endpoints (password branch of `createSession`, standard `createAccount`) for migrated-in accounts.
* **Phase 2:** cross-device login approval — QR-scan (wallet-initiated, phishing-resistant) first; **push-to-approve** later, once the E2E-encrypted notification relay lands (<pull-request id="34230e45-6259-4c9a-b58d-6b135adf84e3" href="https://linear.app/malpercio/review/design-exploration-e2e-encrypted-notification-relay-for-self-hosted-327f880332d1">malpercio-dev/ezpds#207</pull-request>, `docs/design-plans/2026-07-10-notification-relay.md`). Push-approve needs MFA-fatigue mitigations (origin display, number matching).
* **Hard prerequisite (parallel):** the Shamir reconstruction ceremony (or iCloud-synced passkeys), so a lost device is not a total PDS lockout before the password escape hatch is removed.

## Definition of done (exploration → plan promotion)

* Full design plan with acceptance criteria promoted from the exploration doc
* Decision recorded: passkey/WebAuthn vs device-key-signed consent as the primary factor
* Recovery-ceremony dependency scheduled ahead of any password removal
</description>
