### **2. SERVICE-AUTH JWT HANDOFF (PRECISE DETAILS)**

The service-auth JWT is the cryptographic anchor of the entire migration. Here's the exact flow:

#### **Minting on Source (getServiceAuth)**

From `get_service_auth.rs` in the PDS crate (referenced in CLAUDE.md):

- **Caller:** Migration tool or interop wallet
- **Call:** `GET /xrpc/com.atproto.server.getServiceAuth?aud=&lt;dest-did&gt;&amp;lxm=com.atproto.server.createAccount`
- **Auth:** Requires a valid accessJwt for the account being migrated
- **PDS Action:**
  1. Verify the JWT is valid and the subject (account DID) is active
  2. Look up the account's repo signing key (the `#atproto` verification method)
  3. Build a JWT payload:
     ```json
     {
       "aud": "&lt;destination-server-did&gt;",
       "lxm": "com.atproto.server.createAccount",
       "sub": "&lt;migrating-account-did&gt;",
       "iss": "&lt;source-server-did&gt;",
       "exp": &lt;now + 3600&gt;
     }
     ```
  4. Sign with ES256 (P-256 ECDSA) using the account's repo signing key
  5. Return: `{ token: "&lt;jwt&gt;" }`

#### **Verifying on Destination (createAccount migration mode)**

From `create_account_xrpc.rs` in the PDS crate (referenced in CLAUDE.md):

- **Caller:** Migration tool
- **Call:** `POST /xrpc/com.atproto.server.createAccount` with Bearer token set to the JWT
- **Destination Action:**
  1. Extract the JWT from the `Authorization: Bearer &lt;jwt&gt;` header
  2. Decode the JWT header and payload (verify structure)
  3. Fetch the migrating DID document (from plc.directory or local cache) to get its current verification methods
  4. Extract the `#atproto` key from the DID document
  5. Verify the JWT signature using the `#atproto` public key
  6. Confirm the JWT's `aud` matches **this destination server's DID**
  7. Confirm the JWT's `lxm` is **exactly** `com.atproto.server.createAccount`
  8. Confirm the JWT's `exp` is in the future (not expired)
  9. Extract the `sub` (subject) and confirm it matches the request body's `did` field
  10. If all checks pass, create the deactivated account

#### **Key Points:**

- **Signature covers:** `aud`, `lxm`, `sub`, `iss`, `exp` — changing any of these invalidates the signature
- **Audience scoping:** The destination PDS must verify the JWT's `aud` matches its own server DID; otherwise a JWT for destination #1 could be replayed to destination #2
- **Method scoping:** The JWT is scoped to `com.atproto.server.createAccount` only; it cannot be used to call other endpoints
- **Expiration:** Short-lived (typically 1 hour or less with `lxm`; shorter without); migration tools must complete the flow quickly
- **Signing key:** The **account's repo signing key** (the per-account key issued by the source or the PDS), NOT the rotation key. This allows any PDS to issue service-auth tokens for its accounts

```rust
        format!("/xrpc/com.atproto.sync.listBlobs?did={}&amp;cursor={}", did, c)
    } else {
        format!("/xrpc/com.atproto.sync.listBlobs?did={}", did)
    };
    
    // Step 6a: Fetch page of CIDs
    let list_resp = GET &lt;query&gt; (source, public)
    let list_json = parse_json(list_resp)
    
    // Extract CIDs from this page
    let page_cids: Vec&lt;String&gt; = list_json["cids"].as_array()
        .unwrap()
        .iter()
        .map(|v| v.as_str().unwrap().to_string())
        .collect();
    all_cids.extend(page_cids.clone());
    
    // Step 6b: Download and upload each blob in this page
    for cid in page_cids {
        let blob_bytes = GET /xrpc/com.atproto.sync.getBlob?did={}&amp;cid={} (source, public)
        POST /xrpc/com.atproto.repo.uploadBlob (destination, dest_token, blob_bytes)
    }
    
    // Check for pagination
    if let Some(next_cursor) = list_json.get("cursor").and_then(|v| v.as_str()) {
        cursor = Some(next_cursor.to_string());
    } else {
        break;  // No more pages
    }
}

// Step 6c: Verify completeness
loop {
    let missing_resp = GET /xrpc/com.atproto.repo.listMissingBlobs (destination, dest_token)
    let missing_json = parse_json(missing_resp)
    
    if missing_json["blobs"].as_array().unwrap().is_empty() {
        break;  // All blobs uploaded
    }
    
    // If missing exist, error/retry
    if let Some(next_cursor) = missing_json.get("cursor").and_then(|v| v.as_str()) {
        // Continue checking for more missing blobs
        cursor = Some(next_cursor.to_string());
    } else {
        break;  // No more missing-blob pages, but array was non-empty → migration failed
    }
}
```

#### **Termination Condition:**

1. `listBlobs` returns a response with no `cursor` field → all CIDs fetched
2. All CIDs downloaded and uploaded
3. `listMissingBlobs` returns an empty `blobs` array across all pages → transfer complete

### **6. PLC IDENTITY LEG (SELF-SIGNED MIGRATION)**

#### **Wallet-Authorized Path (from `migrate.rs`):**

The wallet does NOT call PDS endpoints for identity. Instead:

1. **Fetch recommended credentials from destination:**
   ```rust
   // Called by the wallet
   let creds_resp = GET /xrpc/com.atproto.identity.getRecommendedDidCredentials
       (destination, dest_oauth_client)
   ```
   Response:
   ```json
   {
     "rotationKeys": [
       "did:key:z...",       // [0] device key (wallet-held)
       "did:key:z..."        // [1] destination's per-account signing key
     ],
     "verificationMethods": {
       "atproto": "did:key:z..."  // [1], same as rotationKeys[1]
     },
     "services": {
       "atproto_pds": {
         "type": "AtprotoPersonalDataServer",
         "endpoint": "https://dest.example.com"
       }
     }
   }
   ```

2. **Build DID-repointing operation locally (NO PDS CALL):**
   - Fetch the current audit log from plc.directory for the DID
   - Extract `prev` (the latest operation CID in the audit log)
   - Build a new operation with:
     - `prev: &lt;latest-cid&gt;`
     - `rotationKeys: [device-key, dest-rotation-key]`
     - `verificationMethods.atproto: dest-rotation-key`
     - `services.atproto_pds.endpoint: https://dest.example.com`
     - Preserve `alsoKnownAs` (handles)
   - Apply the strict pre-sign guard (`guard_migration_op` from migrate.rs)

3. **Sign operation with device key:**
   ```rust
   // From migrate.rs
   let unsigned_bytes = dag_cbor_encode(&amp;operation);
   let signature = device_key.sign(&amp;unsigned_bytes);
   let signed_op = {
     ...operation,
     "sig": base64url(signature)
   };
   ```

4. **Submit to plc.directory (NO PDS CALL):**
   ```rust
   POST https://plc.directory/{did}
   body: signed_op (JSON)
   ```

#### **Interop (PDS-Signed) Path (from the test, step 2):**

The OLD PDS signs the operation using the `signPlcOperation` XRPC endpoint:

1. **Request signature token (email verification):**
   ```rust
   POST /xrpc/com.atproto.identity.requestPlcOperationSignature
       (source, source_token, {})
   // Triggers email to account's verified address
   ```

2. **Sign operation on old PDS:**
   ```rust
   POST /xrpc/com.atproto.identity.signPlcOperation
       (source, source_token, {
         email_token: &lt;token&gt;,
         operation: &lt;partial-op&gt;
       })
   // Returns signed_op ready to submit to plc.directory
   ```

3. **Submit to plc.directory:**
   ```rust
   POST https://plc.directory/{did}
   body: signed_op
   ```

#### **Key Difference:**

- **Wallet-authorized:** Identity operation is built and signed **locally**; plc.directory is the only network call. Source PDS has no role.
- **Interop:** Operation is built locally, but signed by the **old PDS** using an email token. Old PDS must be alive and cooperative.

### **8. STATE &amp; RESUMABILITY**

The Node interop CLI does NOT persist migration state between steps:

```javascript
// From account.js, createAccount():
const persist = (fields) =&gt; {
    state.accounts[name] = { ...(state.accounts[name] ?? {}), ...fields };
    saveState(state);
    return state.accounts[name];
};
```

**State persistence is for account provisioning, not migration.** The CLI:

- Creates ONE account at a time
- Runs the steps sequentially in a single process
- If a step fails, the operator retries manually by re-invoking the CLI

**Idempotency &amp; Retry:**

- **`reserveSigningKey`:** Idempotent (returns the same key if called multiple times)
- **`createAccount` (migration mode):** Idempotent per `did` + `handle` + `email` (409 if account already exists)
- **`importRepo`:** Idempotent (overwrites existing repo blocks)
- **`uploadBlob`:** Idempotent (same CID always produces the same blob record)
- **`activateAccount`:** Idempotent (no-op if already active, no firehose event)
- **`deactivateAccount`:** Idempotent (no-op if already deactivated, no firehose event)

**No resumption capability:** If the migration fails mid-blob-transfer, the tool retries from the beginning of the blob loop (all blobs, not just missing ones). The destination's blob store deduplicates by CID, so re-uploading is safe.
