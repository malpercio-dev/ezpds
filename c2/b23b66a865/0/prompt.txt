<title>Phase 2: Foreign-PDS session provider — password `createSession` unlock path for non-Custos hosts</title>
<description>
Part of <issue id="d5cb6e3d-f781-4ecb-aebf-c954915b3708" href="https://linear.app/malpercio/issue/MM-452/obsign-without-custos-first-class-any-pds-wallet-support-epic">MM-452</issue>. Design: `docs/design-plans/2026-07-24-obsign-without-custos.md` §Phase 2.

## What

Several wallet features are built entirely on standard lexicons but are dark for foreign-hosted identities only because the session that drives them comes from Custos's `/v1/sessions/sovereign`:

* App passwords (`createAppPassword`/`listAppPasswords`/`revokeAppPassword`)
* Change handle (`updateHandle` + the wallet-signed alsoKnownAs op)
* Identity removal (`requestAccountDelete`/`deleteAccount` + tombstone)
* **Blob restore** (`restore_blob_backup`'s `uploadBlob` leg — backup works everywhere, restore doesn't)

`SessionProvider::full_access_client`'s `NeedsUnlock` currently has exactly one resolution: the biometric passwordless `sovereignLogin`. Give it a second: on hosts without the `sovereignSessions` capability (<issue id="e2abaa52-2747-4daf-8c10-209294bd5183" href="https://linear.app/malpercio/issue/MM-454/phase-0b-custos-capability-extension-in-describeserver-self">MM-454</issue>), the unlock cue routes to a password `createSession` prompt (the machinery `source_login.rs` already uses transiently for claim/migration source login), persisting the resulting Bearer pair in the same versioned `{did}:oauth-tokens` record so refresh/rotation flows through the provider's existing ladder unchanged.

## Constraints

* ADR-0021 holds: identity ops need a full session; hosts may email-2FA (`AuthFactorTokenRequired` is already modeled in `PdsClient::create_session`).
* The password is used once and never stored — identical posture to the claim flow.
* Per-feature graceful degradation stays honest: a host that refuses an operation (e.g. no app-password support) surfaces the server's answer, not a wallet guess.

## Acceptance criteria

1. A claimed [bsky.social/reference-PDS](<http://bsky.social/reference-PDS>) identity can mint, list, and revoke app passwords; change handle; run account removal; and restore its blob backup — each behind the same biometric gates as the Custos paths.
2. `SessionError::NeedsUnlock` handling in the frontend branches on host capability: sovereign login (Custos) vs password prompt (other), with 2FA handled.
3. Refresh, host-change discard, and coalescing behavior of `session_provider.rs` are unchanged for Custos identities (existing tests stay green).

<title>Obsign without Custos — first-class any-PDS wallet support (epic)</title>
<description>
## Strategy

Broaden Obsign's market beyond Custos-hosted accounts: a user on the reference PDS, [bsky.social](<http://bsky.social>), or any spec-compliant PDS should get real, honest value from the wallet — Secure-Enclave root key, PLC monitoring + 72h override, user-held repo/media backup, self-held Shamir recovery — with Custos capabilities (escrow-assisted recovery, passwordless sovereign sessions, agents, wallet-confirmed consent) as the opt-in upgrade rather than a lock-in. Rescue and migration must never force a stressed user onto Custos.

Design doc: `docs/design-plans/2026-07-24-obsign-without-custos.md` (survey of what already works without Custos, the ecosystem describeServer survey, the capability-extension design, and phase rationale).

## As-built starting point (verified 2026-07-24, v0.8.1)

Already works on any PDS today: the claim/import flow (device key → `rotationKeys[0]` via standard lexicons), PLC monitoring + recovery override ([plc.directory](<http://plc.directory>) only), repo + blob backup (public sync endpoints, no session), endpoint repair, sovereign share-based recovery (Shares 1+3), and disaster recovery **into a Custos destination**.

Custos-locked today: create ceremony, Shamir generation/re-key (fused to `/v1/dids` + escrow), sovereign sessions (and everything downstream: app passwords, change handle, removal, blob restore), agents/consent, and the rescue/migration **destination** (finalize unconditionally mints `/v1/sessions/sovereign`).

## Phases (one child issue each)

* Phase 0a — mode-select honesty: "Create an identity" / "Import an identity" + non-Custos create gate
* Phase 0b — `custos` capability extension in describeServer + self-identifying `_health`
* Phase 0c — positioning + live validation of the any-PDS arc (claim → backup → rescue)
* Phase 1 — self-held Shamir kit for foreign-hosted identities (escrow-less re-key)
* Phase 2 — foreign-PDS session provider (password `createSession` unlock path)
* Phase 3 — any-PDS rescue/migration destination (capability-gated finalize)

Parked (needs its own design pass, deliberately not in this epic): "create-then-sovereignize" — creating a brand-new account on a reference PDS via standard `createAccount` then immediately running the claim ceremony.
