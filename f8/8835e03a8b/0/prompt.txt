## Critical Issues (count: 1)

- **Issue**: `munge.rs` is labeled `// pattern: Functional Core` and its header asserts "Each munge is a **pure transformation** of the AppView response + local records → merged output." That claim is now false. `get_timeline` (munge.rs:54, 59) and `get_author_feed` (munge.rs:78, 83) `.await` on `viewer.hydrate_quotes(...)` and `viewer.insert_posts_in_feed(...)`, both of which perform outbound HTTP I/O (the service-auth'd `app.bsky.feed.getPosts` call in `viewer.rs:278-361`). A Functional Core must not perform or transitively invoke side effects.
- **Location**: `crates/pds/src/read_after_write/munge.rs:1-4` (and the async I/O call sites at 54, 59, 78, 83)
- **Impact**: The project CLAUDE.md makes the pattern comment a **hard rule**, and the review rubric lists FCIS mislabels (mixed patterns without explanation) as Critical. This is worse than a missing comment: it actively tells a future maintainer that side effects cannot live here, when network I/O now flows through this file. `viewer.rs` — which owns the same I/O — is correctly labeled `Imperative Shell`, making the inconsistency concrete. (Note: `get_profile`/`get_profiles`/`get_actor_likes`/`refresh_own_authored_items`/`is_actor_requester` genuinely are pure; only the two feed-injection paths break purity.)
- **Fix**: Change the pattern comment to `// pattern: Mixed (unavoidable)` and update the header to state that `get_timeline`/`get_author_feed` orchestrate async hydration/insertion through the `LocalViewer` (Imperative Shell) while the profile/likes/refresh/guard helpers remain pure. Alternatively, if the intent is to keep `munge.rs` pure, the hydration + insertion side effects must be lifted into the caller (`pipethrough_munged`) and the munges handed already-hydrated views — but relabeling is the pragmatic, in-scope fix.

## Important Issues (count: 1)

- **Issue**: `extract_actor_param` (mod.rs:208-223) — the URI-query parser that feeds the production actor-guard — has **no direct test**. The guard's *consumers* are tested via direct munge calls passing `Some(did)`/`Some(other)`, but nothing exercises the actual `?actor=&lt;value&gt;` parsing. A regression here (e.g. a wrong NSID guard, mis-split on `&amp;`, or a decode change) would silently make the guard never match in production: own posts would stop appearing in `getAuthorFeed` (AC1.2 fails in the field) with **all tests still green**. This is the exact gap the coverage note called out, and it sits on the load-bearing seam between the untested parser and the tested guard.
- **Location**: `crates/pds/src/read_after_write/mod.rs:208-223`
- **Impact**: The one piece of production logic that decides whether AC1.2 fires at all is unverified. The function is pure and trivially unit-testable (build a `Request`, assert the extracted `Option&lt;String&gt;`), so the gap is cheap to close.
- **Fix**: Add unit tests for `extract_actor_param` covering: (a) `getAuthorFeed` with `?actor=did:plc:x` → `Some("did:plc:x")`; (b) actor not first param, e.g. `?limit=30&amp;actor=alice.bsky.social` → `Some("alice.bsky.social")`; (c) a different NSID (e.g. `getTimeline`) → `None`; (d) `getAuthorFeed` with no `actor` param → `None`; (e) a percent-encoded handle to confirm decoding.

Assessment on the correctness questions raised (no bug found, but documented): the parser is **correct** — `strip_prefix("actor=")` matches only the literal key (so `actorFoo=` is not a false match), works in any query position, returns `None` for non-`getAuthorFeed` NSIDs and when absent, and percent-decodes. The only theoretical limitation is that `urlencoding::decode` does not treat `+` as space, but DIDs (`did:plc:…`) and ATProto handles contain no `+` or reserved characters, so this never bites in practice. The `is_actor_requester` fallback ordering is also **safe**: the `feed[0].post.author.did == requester` last-resort branch runs only after the actor-param checks fail, and in production the param is always threaded, so it cannot pre-empt a correct passthrough for another actor's feed (and a real author feed's items all share the subject anyway).
