The create ceremony (`apps/identity-wallet/src-tauri/src/lib.rs`, `perform_did_ceremony` ~line 594) and the account-migration flow (`apps/identity-wallet/src-tauri/src/migrate.rs` ~line 733) both write the recovery Share 1 to a single **app-global** Keychain slot literal `"recovery-share-1"`, and `confirm_share_backup` (lib.rs ~line 637) reads that global slot. In a multi-identity wallet this is a latent bug: creating or migrating identity B overwrites identity A's Share 1, dropping A's share-based recovery.

MM-411 (the re-key flow, `apps/identity-wallet/src-tauri/src/rekey.rs`) deliberately introduced a **per-DID** slot `recovery-share-1:{did}` (see `recovery_share1_account`) to avoid this. This follow-up should unify create + migration onto the same per-DID scheme:
- Write `recovery-share-1:{did}` in `perform_did_ceremony` and `migrate.rs`.
- Make `confirm_share_backup` per-DID (it currently takes no DID arg — this touches the create-flow frontend contract in `apps/identity-wallet/src/routes/+page.svelte` `confirmBackupAndContinue`, which must thread the DID like the re-key epilogue's `confirmRekeyBackup` already does).
- Consider a one-time migration of any existing global `recovery-share-1` slot to the per-DID slot for the wallet's primary identity.
- The recovery ceremony (MM-410, when built) must read the per-DID slot.

Context: this was noted as a tracked follow-up in `docs/design-plans/2026-07-17-key-recovery-from-shares.md` §7 ("As built") and in the `recovery_share1_account` doc comment in rekey.rs.
