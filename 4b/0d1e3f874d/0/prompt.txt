## Critical Issues (count: 1)

- **Issue**: A genuine `NotFound` whose requested URI is **not** a local post is returned as **HTTP 200 carrying the AppView's `{"error":"NotFound"}` body**, instead of falling back to the original 400.
- **Location**: `crates/pds/src/read_after_write/mod.rs:418` (status override) in combination with `munge.rs:236-237` (Case-B fallthrough returns the original error body unchanged).
- **Trace**:
  1. Client requests `getPostThread?uri=&lt;someone else's post the AppView doesn't know&gt;`.
  2. AppView returns `400 {"error":"NotFound"}` + `atproto-repo-rev` header ⇒ `is_thread_not_found = true`.
  3. Requester happens to have **any** unrelated local record ⇒ `local.count &gt; 0`, so the count==0 gate (mod.rs:332) is passed.
  4. `get_post_thread`: `original` has no `thread` field (Case A skipped); the loop finds no `local_post.uri == requested_uri` ⇒ returns `original` **unchanged** (`{"error":"NotFound",…}`), munge.rs:237.
  5. mod.rs:418 `is_thread_not_found &amp;&amp; status.is_client_error()` = `true &amp;&amp; true` ⇒ **status forced to 200 OK**, but the body is still the error envelope.
- **Impact**: A real NotFound is masked as success. The client receives `200 OK` with a body that has no `thread` and instead an `error` field — malformed per the `getPostThread` lexicon. This directly violates the plan's stated fallback contract and can misrender in clients that branch on HTTP status. The override keys only on `is_thread_not_found`, never on whether reconstruction actually produced a thread; the munge returns `Value` with no success/failure signal, so the two outcomes are indistinguishable at the override site.
- **Why the AC tests miss it**: AC3.1 only exercises the case where `requested_uri` **is** a local post. There is no test for "NotFound + local records present + requested_uri not local." Confirmed no such assertion exists in the suite.
- **Fix**: Gate the override on the munged output actually being a reconstructed thread. `munged` (the `serde_json::Value`) is still in scope at line 418. For example:
  ```rust
  let reconstructed = munged.get("thread").map(|t| !t.is_null()).unwrap_or(false);
  let response_status = if is_thread_not_found &amp;&amp; status.is_client_error() &amp;&amp; reconstructed {
      axum::http::StatusCode::OK
  } else {
      status
  };
  ```
  Add a regression test: NotFound body + a local post whose URI ≠ the requested URI ⇒ assert `resp.status() == 400` and the body still carries `error == "NotFound"`.

## Important Issues (count: 1)

- **Issue**: Case A splices local replies by **appending to the end** of `thread.replies` rather than merging in `createdAt`/`indexedAt` order. The code even computes the sort (`replies_to_add.sort_by(... b.0.cmp(&amp;a.0))`, munge.rs:176) and then discards its effect by pushing onto the existing array (lines 178-182), so the sort is dead work and ordering across AppView-vs-local replies is not honored.
- **Location**: `crates/pds/src/read_after_write/munge.rs:174-189`.
- **Impact**: Own fresh replies always sink below the AppView's existing replies regardless of recency. The plan asks for createdAt ordering; it also permits "shallow/best-effort," so this is a quality gap rather than a correctness failure for the AC (AC3.2 only asserts presence, not position). The internal inconsistency (sort computed but unused) is a maintenance smell worth resolving even if end-append is kept deliberately.
- **Fix**: Either merge-sort the combined replies by the reply post's `indexedAt`/`createdAt`, or drop the now-pointless `sort_by` and add a one-line comment stating end-append is the intentional best-effort behavior.
