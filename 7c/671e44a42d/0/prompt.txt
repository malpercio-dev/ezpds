<title>Phase 3: Any-PDS rescue and migration destination — capability-gated finalize</title>
<description>
Part of <issue id="d5cb6e3d-f781-4ecb-aebf-c954915b3708" href="https://linear.app/malpercio/issue/MM-452/obsign-without-custos-first-class-any-pds-wallet-support-epic">MM-452</issue>. Design: `docs/design-plans/2026-07-24-obsign-without-custos.md` §Phase 3.

## Why

Recovering an account is the worst possible moment to present a hosting decision with only one viable answer. Today every leg of sovereign disaster recovery (`disaster_recovery.rs`) and outbound migration works against any PDS — offline service-auth JWT verified via [plc.directory](<http://plc.directory>), standard `createAccount`/`importRepo`/`uploadBlob`/`activateAccount` — **except** the finalize: `finalize_migration_core` unconditionally mints the destination sovereign session via `/v1/sessions/sovereign`, which only Custos serves. A reference-PDS destination would die at the last step, after the identity op already landed.

## What

Branch the injected `ensure_session` step on the destination's `sovereignSessions` capability (<issue id="e2abaa52-2747-4daf-8c10-209294bd5183" href="https://linear.app/malpercio/issue/MM-454/phase-0b-custos-capability-extension-in-describeserver-self">MM-454</issue>):

* **Capability present (Custos):** today's behavior — mint + persist the sovereign session before deactivating the source.
* **Capability absent:** durably persist the Bearer session already held from the migration `createAccount` (via the existing `OAuthClient::new_bearer` + versioned `{did}:oauth-tokens` record) as the destination credential, preserving the strict activate → durable-credential → deactivate ordering. Post-cutover session lifecycle then rides Phase 2's password unlock path (<issue id="7d621f07-95f0-490d-a547-4f75b3e9f24c" href="https://linear.app/malpercio/issue/MM-457/phase-2-foreign-pds-session-provider-password-createsession-unlock">MM-457</issue>).

Same branch serves both flows for free: sovereign disaster recovery to a non-Custos destination, and normal outbound migration between two non-Custos hosts.

## Acceptance criteria

1. Disaster recovery rebuilds an account onto a reference PDS end-to-end from the iCloud backups, with the same abort-safety ordering (a credential-persistence failure leaves nothing half-live and is retryable).
2. Outbound migration to a non-Custos destination finalizes without ever calling `/v1/sessions/sovereign`.
3. Custos-destination behavior is byte-identical to today (existing orchestrator tests unchanged).
4. The destination-picker UI presents Custos and other-PDS destinations with equal weight — the Custos pitch is its capabilities, not the only working button.

Depends on <issue id="e2abaa52-2747-4daf-8c10-209294bd5183" href="https://linear.app/malpercio/issue/MM-454/phase-0b-custos-capability-extension-in-describeserver-self">MM-454</issue> (capability probe); post-cutover authenticated features on a non-Custos destination depend on <issue id="7d621f07-95f0-490d-a547-4f75b3e9f24c" href="https://linear.app/malpercio/issue/MM-457/phase-2-foreign-pds-session-provider-password-createsession-unlock">MM-457</issue>.
</description>

<title>Obsign without Custos — first-class any-PDS wallet support (epic)</title>
<description>
## Strategy

Broaden Obsign's market beyond Custos-hosted accounts: a user on the reference PDS, [bsky.social](<http://bsky.social>), or any spec-compliant PDS should get real, honest value from the wallet — Secure-Enclave root key, PLC monitoring + 72h override, user-held repo/media backup, self-held Shamir recovery — with Custos capabilities (escrow-assisted recovery, passwordless sovereign sessions, agents, wallet-confirmed consent) as the opt-in upgrade rather than a lock-in. Rescue and migration must never force a stressed user onto Custos.

Design doc: `docs/design-plans/2026-07-24-obsign-without-custos.md` (survey of what already works without Custos, the ecosystem describeServer survey, the capability-extension design, and phase rationale).

## As-built starting point (verified 2026-07-24, v0.8.1)

Already works on any PDS today: the claim/import flow (device key → `rotationKeys[0]` via standard lexicons), PLC monitoring + recovery override ([plc.directory](<http://plc.directory>) only), repo + blob backup (public sync endpoints, no session), endpoint repair, sovereign share-based recovery (Shares 1+3), and disaster recovery **into a Custos destination**.

Custos-locked today: create ceremony, Shamir generation/re-key (fused to `/v1/dids` + escrow), sovereign sessions (and everything downstream: app passwords, change handle, removal, blob restore), agents/consent, and the rescue/migration **destination** (finalize unconditionally mints `/v1/sessions/sovereign`).

## Phases (one child issue each)

* Phase 0a — mode-select honesty: "Create an identity" / "Import an identity" + non-Custos create gate
* Phase 0b — `custos` capability extension in describeServer + self-identifying `_health`
* Phase 0c — positioning + live validation of the any-PDS arc (claim → backup → rescue)
* Phase 1 — self-held Shamir kit for foreign-hosted identities (escrow-less re-key)
* Phase 2 — foreign-PDS session provider (password `createSession` unlock path)
* Phase 3 — any-PDS rescue/migration destination (capability-gated finalize)

Parked (needs its own design pass, deliberately not in this epic): "create-then-sovereignize" — creating a brand-new account on a reference PDS via standard `createAccount` then immediately running the claim ceremony.
