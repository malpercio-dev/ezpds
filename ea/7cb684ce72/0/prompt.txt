## Important Issues (count: 1)

- **Issue**: The "two-layer buffer cap" does not bound peak memory when the upstream omits or lies about `Content-Length`. `upstream.bytes().await` (`mod.rs:296`) fully buffers the entire body into memory *before* the post-buffer length check at line 299. `reqwest::Response::bytes()` has no internal size limit, so a chunked-encoded or `Content-Length`-absent response is buffered in full regardless of `MAX_MUNGE_RESPONSE_BODY`; the check then rejects it *after* the allocation.
- **Location**: `crates/pds/src/read_after_write/mod.rs:282-309`
- **Impact**: Under a broken/malicious AppView (or MITM) using chunked transfer, the cap provides correctness (rejects oversized) but not memory-DoS protection. The `content_length()` early-bail only helps honest upstreams.
- **Assessment**: This is **plan-sanctioned** — phase_07.md line 48 explicitly calls it "a guard, not a hard bound," and the upstream is the trusted configured AppView. The overflow path is safe (clean `500`, no panic/truncation). Flagging because the code comment ("guards against unbounded buffering") slightly overstates the guarantee.
- **Fix (optional, for a future hardening pass)**: bound the read itself — stream `bytes_stream()` accumulating up to `MAX+1` and reject on exceed, or use `http-body-util`'s `Limited`. Not required to merge given the trust boundary; consider tightening the doc-comment wording to say the cap bounds the *accepted* size, not peak buffering, when content-length is absent.
