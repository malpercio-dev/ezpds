# Brainstorming Ideas Into Designs

## Overview

Transform rough ideas into fully-formed designs through structured questioning and alternative exploration.

**Core principle:** Ask questions to understand, explore alternatives, present design incrementally for validation.

**Announce at start:** "I'm using the brainstorming skill to refine your idea into a design."

```
Example (WRONG):
```

```
   Token is consumed on first click, session created immediately. Simple flow. User can't re-click the link. Standard pattern for passwordless auth.
2. Token valid for multiple users within TTL

3. Token with idempotent verification
```

- Use TaskUpdate to mark Phase 3 as in_progress

**Level of detail:** Present architecture and components, not implementation code.

- **Contracts/interfaces: OK.** If a component exposes an API or interface that other systems depend on, show the shape (types, method signatures, request/response formats).
- **Implementation code: NOT OK.** Function bodies, algorithms, and executable logic belong in implementation plans, not design.

The distinction: contracts define boundaries between components. Implementation defines behavior within components. Brainstorming validates the boundaries; implementation planning fills in the behavior.

**Output:** Validated design held in conversation context, ready for documentation.

Pairing is the one moment the system bootstraps trust, so it's worth being precise. Five steps:

1. **Operator mints a pairing code** from the laptop: `POST /v1/admin/pairing-codes` with the master token → relay returns `{ pairing_code, expires_at }`. A `just admin-pair` recipe renders it as a QR in the terminal that also encodes the relay base URL: `{ "url": "https://relay…", "code": "…" }`.

2. **Phone scans the QR** → now it knows where the relay is and holds the one-time code.

3. **Phone generates its admin keypair in the Secure Enclave** (reusing the `device_key.rs` pattern) → gets a `did:key:z…` public key it can present but whose private half can never leave the device.

4. **Phone claims the code**, proving key possession: `POST /v1/admin/devices` with body
   ```
   { "pairing_code": "...", "label": "Jacob's iPhone",
     "public_key": "did:key:z...", "platform": "ios",
     "signature": "<r‖s over (pairing_code ‖ public_key ‖ timestamp)>",
     "timestamp": "..." }
   ```
   The relay verifies the code is valid/unconsumed/unexpired **and** that the signature checks out against the supplied public key — so it only ever stores a key the phone actually controls. It inserts an `admin_devices` row, marks the code consumed in the same transaction, and returns `{ device_id }`. No long-lived secret is ever transmitted.

5. **Done.** From here the phone authenticates every request by *signing it* (Section 3) — there's nothing to "log in" with.

Agent: ## Design — Section 3 of 5: The signed-request scheme & verification

There's no session and no bearer token in flight — the phone authenticates *each request* by signing it. Every admin call carries four headers:

```
X-Admin-Device:     <device_id>          ← which pubkey to check
X-Admin-Timestamp:  <unix seconds>
X-Admin-Nonce:      <random 128-bit>
X-Admin-Signature:  <base64url(r‖s)>      ← Secure-Enclave signature
```

**What gets signed** is a canonical string binding the whole request, so a captured signature can't be replayed onto a different route or body:

```
sign_string = method  ‖ "\n" ‖
              path     ‖ "\n" ‖
              timestamp‖ "\n" ‖
              nonce    ‖ "\n" ‖
              sha256(body)
```

The phone signs `sha256(sign_string)`'s preimage via `device_key::sign(...)`, identical to how Obsign signs genesis ops today.

**Relay verification** — `require_admin(headers, body, state)` replaces `require_admin_token` and accepts two credentials:
1. **Break-glass:** a valid `Authorization: Bearer <master>` → allow (keeps CI/Bruno working untouched).
2. **Admin device:** look up `device_id` → reject if revoked; reject if `|now − timestamp| > 60s`; rebuild `sign_string`, verify `r‖s` against the device's stored did:key via a new `crypto::verify_p256_signature(pubkey, msg, sig)` (a thin public wrapper over the existing internal `verify_signature_with_key`); then **insert the nonce into an `admin_nonces` table with a UNIQUE constraint** — a conflict means replay, so reject. On success, bump `last_seen_at`.
