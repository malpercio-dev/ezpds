In Tauri v2, there is no automatic "allow by default" for app commands; all access must be explicitly granted via the capabilities system [1][2]. If a window or webview is not associated with a capability that grants it specific permissions, it has no access to the IPC layer [2]. Key points regarding permissions and commands: Capabilities and Core Default: The core:default permission is a special, simplified permission set introduced to include all default permissions from all core plugins [3]. It is commonly referenced within a capability file (e.g., in src-tauri/capabilities/default.json) to grant standard application functionality without listing every individual core plugin permission [4][3][5]. App Commands vs. Plugin Commands: Permissions for commands directly implemented in your application (app commands) do not require a plugin prefix [2]. However, like plugin commands, they must be explicitly defined and enabled in your capability configuration to be accessible [6][2]. Autogenerated Permissions: When you create a new command, the Tauri build system automatically generates permission files for it (visible in src-tauri/permissions/autogenerated/commands) [7]. By default, these generate enable and deny permissions, but these must still be manually added to a capability for them to be active [7]. Permission Resolution: Permissions are defined in TOML files, and capabilities are defined in JSON (or JSON5/TOML) [8]. A capability maps these permissions to specific windows or webviews [1][2]. If a command is included in both allow and deny lists within a permission, it is denied by default [9].
