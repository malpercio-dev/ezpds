# FCM as the relay's second transport: facts

Gathered 2026-11-07 from Firebase, Google Identity and Android documentation, for wayfinder map MM-613. This note records facts only; the design decision belongs to a later ticket. Anything the documents did not state is marked **unconfirmed**.

## What the APNs side does today

- `crates/notify-relay/src/protocol.rs`: requests are capped at 64 KiB (`MAX_MESSAGE_LEN`). `apns_envelope(kid, enc, ct)` builds the body: a fixed content-free `aps` alert plus `"ezpds": {v, kid, enc, ct}`. The padding buckets are defined on this body's serialized length and modelled on the sender (Custos) side.
- `crates/notify-relay/src/apns.rs`: `MAX_PAYLOAD_BYTES = 4096` on the serialized body, checked before contacting Apple (`TooLarge`). The provider token is a hand-rolled ES256 JWT (`iss`, `iat`, no `exp`) reused for 50 minutes. Default expiry is 3600 s via `apns-expiration`. Only a 410 maps to `PushOutcome::Unregistered`, which makes the instance delete the registration. 400 and 403 are deliberately not read as a dead device.

## 1. Message shape

- `message.data` is "a map of string keys to string values" ([REST reference: projects.messages](https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages)). A data-only message omits `notification`; the client app processes it ([message types](https://firebase.google.com/docs/cloud-messaging/customize-messages/set-message-type)).
- Limit: "Maximum payload for both message types is 4096 bytes" ([message types](https://firebase.google.com/docs/cloud-messaging/customize-messages/set-message-type)). That page does **not** say what is measured (keys, values, or the whole `message` JSON). **Unconfirmed**: treat it conservatively as the whole serialized message and test against the live API.
- Reserved keys: `from`, `message_type`, anything starting `google.` or `gcm.notification.` (REST reference); the message-types page also warns against `gcm.`.
- Implication, hedged: one base64url string value is a legal carrier. Unlike APNs there is no fixed `aps` alert block, so the envelope overhead is smaller (the `kid`/`enc`/`ct` keys, JSON quoting, and the `message`/`token`/`android` wrapper if the whole request counts). The APNs buckets, defined against a 4096-byte body that includes the alert, should therefore fit, but the headroom depends on the unconfirmed measurement rule. Padding must be computed against whichever serialization is actually counted.

## 2. Delivery

- Priority (v1 `AndroidConfig`): NORMAL "won't open network connections on a sleeping device"; HIGH "FCM attempts to deliver ... immediately" ([REST reference](https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages), [message priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority)). In Doze, normal-priority delivery "may be delayed" until Doze exits; high priority can wake a sleeping device and grants limited processing.
- Throttling of high priority: if FCM "detects a pattern in which messages don't result in user-facing notifications" it may lower them to normal priority or proxy them; evaluated over 7 days per app instance ([message priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority)). A data message the app turns into a local notification counts as user-facing; a content-free ping that shows nothing is exactly the pattern at risk. No numeric per-device quota is documented there.
- **New, load-bearing**: the Android Doze page now says "v1 of FCM used high priority messages whereas v2 uses `RemoteNotification` ... and `BackgroundSync` for non-urgent messages ... We strongly recommend migrating to v2 as v1 is deprecated" ([Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)). The v2 API (`message.android_v2`) is documented as **preview (Pre-GA)**, with an EAP client SDK (`26.1.0-eap01`). `RemoteNotification` can carry encrypted `data` plus a generic fallback `notification`, with `mutable_content: true` to decrypt in `onNotificationReceived()` (20 s limit); background suppression above 25% posts the fallback. `BackgroundSync` "may be delayed or throttled". The v2 page states no payload limit, no error codes, and no sunset date for v1 ([v2 API](https://firebase.google.com/docs/cloud-messaging/send/v2-api)). This is structurally closer to the APNs Notification Service Extension model than a v1 data message. Whether v1 `android.priority: HIGH` keeps working, and until when, is **unconfirmed**.
- `onMessageReceived` by app state (v1): data messages reach it in foreground and background ([receive messages](https://firebase.google.com/docs/cloud-messaging/android/receive-messages)). It "has a short execution window"; long work goes to WorkManager.
- Killed or force-stopped: the Firebase pages do not address it. **Unconfirmed from primary sources.** Secondary sources attribute non-delivery to Android's stopped state; the Android Intent reference was too large to read for `FLAG_EXCLUDE_STOPPED_PACKAGES` ([Intent](https://developer.android.com/reference/android/content/Intent)). Treat force-stop as undeliverable until verified.
- `ttl`: duration string such as `"3.5s"`; default and maximum 4 weeks; `0` sends immediately. `collapse_key`: "A maximum of 4 different collapse keys is allowed at any given time" ([REST reference](https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages)). Messages are non-collapsible by default ([v2 API](https://firebase.google.com/docs/cloud-messaging/send/v2-api)). So `ttl` maps to `apns-expiration` (APNs takes an absolute time, FCM a relative duration) and `collapse_key` to `apns-collapse-id`, with a 4-key ceiling.

## 3. Sending

- Endpoint: `POST https://fcm.googleapis.com/v1/projects/PROJECT_ID/messages:send`, body `{"message": {...}}`, header `Authorization: Bearer <access token>` ([send via HTTP v1](https://firebase.google.com/docs/cloud-messaging/send/v1-api)).
- Scope: `https://www.googleapis.com/auth/firebase.messaging` ([authorize send requests](https://firebase.google.com/docs/cloud-messaging/auth-server)); the REST reference also accepts `cloud-platform`.
- Service-account exchange ([Google OAuth 2.0 for service accounts](https://developers.google.com/identity/protocols/oauth2/service-account)): POST to `https://oauth2.googleapis.com/token`, form fields `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` and `assertion=<JWT>`. JWT header `alg: RS256` ("the only signing algorithm supported"), `typ: JWT`, optional `kid`. Claims: `iss` (service-account email), `scope`, `aud` (`https://oauth2.googleapis.com/token`), `iat`, `exp` (at most 1 hour after `iat`). The response carries `access_token`, `token_type: Bearer`, `expires_in` (3600 in the example; reusable for that window). Contrast APNs: ES256, no `exp`, no exchange step. FCM adds a token round trip and a cached access token.
- Errors ([FCM error codes](https://firebase.google.com/docs/reference/fcm/rest/v1/ErrorCode)): `UNREGISTERED` 404 ("App instance was unregistered from FCM"); `INVALID_ARGUMENT` 400 (malformed request, including payload size, reserved keys, TTL, token format); `SENDER_ID_MISMATCH` 403 ("The authenticated sender ID is different from the sender ID for the registration token"); `QUOTA_EXCEEDED` 429; `UNAVAILABLE` 503; `INTERNAL` 500; `THIRD_PARTY_AUTH_ERROR` 401 (APNs/web push credentials, not relevant to Android).
- Drop-for-good: FCM's token guidance says for `UNREGISTERED` "it is safe to delete your record of this registration, since it will never again be valid"; `INVALID_ARGUMENT` signals an invalid registration "only if the payload is otherwise valid" ([manage tokens](https://firebase.google.com/docs/cloud-messaging/manage-tokens)). So only 404 `UNREGISTERED` mirrors APNs 410. 400 is ambiguous exactly as APNs 400 is, and `SENDER_ID_MISMATCH` is a relay credential or configuration fault (inferred), so it should not drop a handle.
- Limits ([scale FCM](https://firebase.google.com/docs/cloud-messaging/scale-fcm)): HTTP v1 gives 600K quota tokens per 1-minute bucket per project, one per request. 429 may carry `retry-after`; default wait 60 s; minimum 10 s before retrying a failure; give up after 60 minutes of backoff. No per-device throttle is documented on that page.

## 4. Registration tokens

- A token is an opaque string identifying the app instance ([architecture](https://firebase.google.com/docs/cloud-messaging/fcm-architecture)). **Length: not stated** in any page read; treat as opaque text (the register RPC is far inside the 64 KiB cap).
- Rotation: `onNewToken` fires on first generation and on change; documented causes are restoring to a new device, uninstall and reinstall, and clearing app data ([Android client](https://firebase.google.com/docs/cloud-messaging/android/client)). Stale after about a month without connecting; expired after 270 days inactive on Android ([manage tokens](https://firebase.google.com/docs/cloud-messaging/manage-tokens)).
- **Also new**: the Android client and manage-tokens pages mark `getToken()` registration tokens deprecated in favour of Firebase Installation IDs (FID), with `onRegistered()` described as the equivalent callback, and the REST `token` field is marked deprecated in favour of `fid` ([REST reference](https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages)). Migration timeline **unconfirmed**; the register RPC may want an opaque target string rather than a token-specific name.
- Project binding: the architecture and client pages do not state it. The error table implies it: a sender ID different from the one the token registered with returns 403 `SENDER_ID_MISMATCH`. So a push to project A's token authenticated as project B fails with `SENDER_ID_MISMATCH` (inferred; the docs do not walk through this scenario).

## 5. Self-hosting

- Sending requires an OAuth token from a service account that holds permission on the target project ([authorize send requests](https://firebase.google.com/docs/cloud-messaging/auth-server)). The documented cross-project case is explicit: the target project must assign the Firebase Cloud Messaging API Admin role to the sender's service account, and the request goes to the target project's endpoint. Sending is therefore gated by the project owner's IAM, the same structure as the APNs `.p8`. Nothing in the pages read lets a third party send to a project's installs without that grant.
- Consequence: a self-hoster either has their own Firebase project (and ships their own app build, because tokens are bound to a sender, section 4), or is granted the role on the official project by its owner. The grant route is documented but is a trust decision, not a default. That a separate app build is needed is inferred from the sender-ID binding, not stated as such.

## 6. Dependencies

- The workspace `reqwest` is `0.13` with `rustls` and `http2` features and no OpenSSL (root `Cargo.toml`). That covers both calls: the `oauth2.googleapis.com/token` form POST and the `fcm.googleapis.com` JSON POST.
- Needed beyond that: RS256 signing over the service account's RSA private key (PKCS#8 PEM inside the JSON key file), plus parsing that JSON file (`serde_json` is already available).
- `Cargo.lock`: `jsonwebtoken 9.3.1` is present (used by `pds`, `custos-core`, `custos-oauth`, `custos-agents`, `custos-blobs`, `custos-spaces`; it depends on `ring`); `ring 0.17.14` and `aws-lc-rs 1.18.2` are present (rustls depends on both); there is **no `rsa` crate**. `notify-relay` depends on none of `jsonwebtoken`, `ring`, `aws-lc-rs` directly (it uses `p256`, and its Cargo.toml comment explains it avoided `jsonwebtoken` for ES256). Adding `jsonwebtoken` (or `ring`) to `notify-relay` adds an edge but no new package. `p256` cannot sign RS256.
