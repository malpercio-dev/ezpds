# Database Module (`pds`)

Last verified: 2026-10-21

Query modules only `pds` reads. The pool, the migration log and runner, `DbError`, and the
cross-feature query modules (`accounts`, `dids`, `handles`, `blobs`, `blocks`, `kek`,
`admin_audit`, `sessions`, `refresh_tokens`, `server_stats`, `oauth`) live in
[`crates/custos-db`](../../../custos-db/AGENTS.md), which also holds the migration log and the
migration invariants. `mod.rs` re-exports that API, so `crate::db::…` paths resolve unchanged.

A new table's migration goes in `custos-db`; its query module goes here unless a second crate
reads it, or a feature crate owns the table (the Spaces tables' queries live in
[`custos-spaces`](../../../custos-spaces/AGENTS.md)).

## Key Files

- `app_passwords.rs` - Query functions for V031/V063: `insert_app_password` (reports `DuplicateName` on the `(did, name)` PK collision → 409), `list_app_passwords` (public metadata, no hash), `list_verify_candidates` (name + hash + grants, for `createSession` to try a supplied password against), `app_password_grants` (re-derive an app-pass session's `privileged` + `personal_details` grants on `refreshSession`). Revocation (delete the row + its refresh tokens/sessions) is a multi-table transaction owned by `routes/revoke_app_password.rs`, not here
- `waitlist.rs` - Query functions for V057: `insert_signup` (+ `InsertSignupOutcome` — the unique-violation arm makes a repeat signup an idempotent no-op), `list_signups` (newest-first rowid-cursor page for the operator readout), `count_signups`
- `admin_devices.rs` - Query functions for V025: `insert_pairing_code`/`get_pairing_code`/`consume_pairing_code` (single-use, atomic), `insert_device`/`get_device`/`list_devices`/`revoke_device` (idempotent) + `touch_last_seen` (liveness bump after a device signed request authenticates), `insert_nonce_if_absent` (replay-rejecting) + `sweep_stale_nonces` (wired to the periodic `admin_nonce_sweep.rs` background task; pure storage reclamation, not a replay-safety control — the `(device_id, nonce)` primary key already enforces that, and config validation keeps retention above the request's full replay-acceptance window so a swept row can never still be within it). Transactional ones are generic over the executor so the Phase 3 register-device flow can consume a code and insert the device atomically
- `sovereign_session_nonces.rs` - Atomic insert-if-absent and timestamp-window-safe stale-nonce sweeping for sovereign-session proofs
- `account_deletion_tokens.rs` - Query functions for V034: `insert_account_deletion_token` (1-hour TTL) and `consume_account_deletion_token` (atomic single-use redemption bound to `(token_hash, did)`)
- `email_tokens.rs` - Query functions for V036: `insert_email_token` (1-hour TTL) and `consume_email_token` (atomic single-use redemption bound to `(token_hash, did, purpose)`), plus the `EmailTokenPurpose` (`Confirm`/`Update`) enum
- `repo_keys.rs` - Query functions for pending-account repo signing keys, reserved account-migration signing keys, and promoted DID-keyed signing keys. Since V048 rows carry a `status` (`active`|`staged`): the commit-signer lookup (`get_signing_key_by_did`) reads `'active'` rows only, and the rotation trio `stage_rotation_key` (delete-and-insert a fresh `'staged'` row) / `get_staged_signing_key` / `promote_staged_signing_key` (cutover: staged → active + delete retired active rows, one transaction) backs the `/v1/repo-keys/rotation` surface
- `notifications.rs` - Query functions for V058: the sender-key set (`list_publishable_sender_keys` — active + retired, never revoked, newest first: exactly what the two `sender-keys` routes publish; `get_active_sender_key` — the newest unretired key, what seals; `insert_sender_key`; the idempotent `retire_sender_key`/`revoke_sender_key`) and the two registration surfaces (`upsert_registration`/`list_registrations`/`set_registration_handles_for_token`/`delete_registration`, and the admin `upsert_admin_registration`/`list_active_admin_registrations`/`admin_registration_handle`/`set_admin_registration_handles_for_token`/`delete_admin_registration`). Three deliberate shapes: the handle write-back is keyed on **`apns_token`**, not on the `(did, device_uuid)` whose request minted it, because the token is the relay's rotation key — one token has one live handle, so a device holding several identities here needs every one of their rows carried forward by each mint (a per-DID write-back left all but the last naming a rotated-away handle, whose pushes the relay refuses as `unknownHandle` — not a prune signal, so the rows survived to fail again); the admin fan-out query **joins `admin_devices` on `revoked_at IS NULL`**, so revoking a device stops its pushes immediately without waiting for the cleanup delete, while `admin_registration_handle` is status-*independent* precisely because the revoke cleanup runs after the tombstone is stamped and would otherwise find nothing; and `RegistrationRow` omits `apns_token`/`apns_topic` (written from the request body, known to the relay by handle — selecting them would invite a delivery decision from a stale copy of Apple's routing state).
- `recovery_escrow.rs` - Query functions for V050's escrow table: `escrow_share_exists`, `insert_escrow_share`, `replace_escrow_share` (stamps `rotated_at`, clears in-flight release state), `delete_escrow_share` (reports whether a row existed, so the caller audits only real deletions), plus the release state-machine helpers: `get_release_state` (+ `ReleaseState`; reads the ciphertext + in-flight/available flags, `None` for an escrow-less account so escrow presence is never an oracle), `open_release` (stamp `release_requested_at`/`release_pending_until = now + delay`), `clear_release` (guarded on an in-flight release, so the caller audits only real cancels/releases — shared by the cancel endpoint and the post-delivery clear), and `list_pending_releases` (+ `PendingRelease`; the operator visibility list, never selecting the share). Generic over the executor; the transactions live in `routes/recovery_escrow.rs` and `routes/recovery_release.rs`
- `recovery_otps.rs` - Query functions for V053: `insert_recovery_otp` (1-hour TTL) and `consume_recovery_otp` (atomic single-use redemption bound to `(token_hash, did)`), the email OTP gating `POST /v1/recovery/release`. Same hashed envelope as `account_deletion_tokens` (V034)
- `recovery_audit.rs` - Query functions for V050's append-only escrow audit trail: `RecoveryAuditEventType` (`deposited`/`rotated`/`deleted`; release-flow vocabulary reserved by the schema CHECK) + `insert_recovery_audit_event` (generic over the executor for in-transaction writes). INSERT only — no UPDATE/DELETE exists or may be added; `purge_account` is the sole remover
- `plc_operation_tokens.rs` - Query functions for V033: `insert_plc_operation_token` (1-hour TTL) and `consume_plc_operation_token` (atomic single-use redemption bound to `(token_hash, did)`)
- `transfers.rs` - Query functions for V027/V029/V030: `insert_transfer` opens a `pending` transfer (sweep-then-insert), returning `InitiateOutcome::{Created, DuplicateActive, CodeCollision}` — a `did` index violation is the per-account 409 path, a `code` violation triggers the caller's regenerate-and-retry; accept helpers store the promoted target credential; complete helpers authenticate source/target tokens, revoke superseded credentials, mark terminal, and insert the audit event
