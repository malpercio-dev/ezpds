## Human Test Plan

The 5 HV-* items exist because wiremock can reproduce the AppView's response *shape* but not the *real* AppView/CDN behavior the mechanisms depend on. These require a **deployed, federated ezpds PDS** with a real account, pointed at the real Bluesky AppView (`https://api.bsky.app`) and CDN (`https://cdn.bsky.app`).

### Prerequisites

- A deployed ezpds PDS federated into the atproto network (per `docs/project_federation_readiness.md`: `EZPDS_PUBLIC_URL` set to the DID-doc `serviceEndpoint`, wildcard DNS + TLS live, blobs publicly resolvable via `getBlob`).
- A real account on that PDS with a valid session (full-access token).
- `[appview] url = https://api.bsky.app` (default) and `EZPDS_APPVIEW_CDN_URL` default (`https://cdn.bsky.app`).
- `curl`, a real Bluesky client (official app or a web client) authenticated to the PDS account.
- Baseline confidence: `nix develop --impure --accept-flake-config -c cargo test -p pds read_after_write` green (55/55, confirmed).

### HV-1 — Real AppView emits `atproto-repo-rev` (underpins AC5.1, AC7.1, AC4.4)

Purpose: the entire selection boundary keys off this header; wiremock sets it by fiat.

| Step | Action | Expected |
|------|--------|----------|
| 1 | `curl -i -H "Authorization: Bearer &lt;token&gt;" "https://&lt;pds-host&gt;/xrpc/app.bsky.actor.getProfile?actor=&lt;your-did&gt;"` | 200; response headers include `atproto-repo-rev: &lt;value&gt;` |
| 2 | Note the header value; compare it (TID string-ordering) against your account's current repo rev (from a fresh local commit, e.g. after a `putRecord`) | Header value is a repo rev (TID) that string-compares sensibly (`&lt;=` current head) |
| 3 | Repeat for `getTimeline` | Header present on this endpoint too |

If the header is absent, read-after-write silently no-ops (the AC5.3 empty-LocalRecords path). This check confirms it does not.

### HV-2 — Fresh avatar/banner/image CDN URLs resolve to real images (confirms AC2.4, AC1.5, AC2.3)
