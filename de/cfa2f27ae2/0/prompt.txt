### Critical #2 — `indexed_at` is stamped with a single global commit time, not each record's own commit time
- **Issue:** The plan requires collecting "the newest `CommitEvent.time` seen per key" (phase_02.md line 98–99) and setting `indexed_at = the kept CommitEvent.time` (line 107). The implementation instead captures one global `kept_time` = the time of the newest commit in the walk (mod.rs lines 79–81, set only `if kept_time.is_none()`), and applies that same value to **every** record (line 143: `let indexed_at = kept_time.clone().unwrap_or_default();`). The `touched` map stores `event.rev` as its value and never the per-key time, so per-record time is not tracked at all.
- **Location:** `crates/pds/src/read_after_write/mod.rs:51`, `:79-81`, `:143`.
- **Impact:** All merged records share one timestamp (the newest commit's). This corrupts `indexedAt` for feed ordering (AC5.1's downstream munges) and defeats AC4.3's contract — `local_lag_ms` is documented and tested as "milliseconds since the **oldest** merged record's indexed_at," but on real data every record is identical, so the lag reflects the newest commit rather than the oldest write. It only appears correct in the hand-built `local_lag_ms` unit tests (which set distinct timestamps manually); the real production path can never produce the intended distinction. A record deleted in the newest commit but re-read from an older commit would also mis-stamp.
- **Fix:** Track the newest `CommitEvent.time` per `(collection, rkey)` in the `touched` map (e.g. store a small struct or `(rev, time)` and, since you walk newest-first, keep the first-seen time for each key). Use that per-key time as the record's `indexed_at` instead of the global `kept_time`.

## Important Issues (count: 1)

### Important #1 — Redundant second MST lookup for the CID; the op `cid` is discarded
- **Issue:** For each touched key the code calls `get_record_json` and then a separate `get_record_cid` (mod.rs lines 122 and 133) — two MST traversals per record. The plan explicitly notes the op `cid` from the decoded `RepoOp` is available (`RepoOp.cid: Option&lt;String&gt;`, and `op.at_uri(did)` helpers already exist in `firehose.rs`), and suggests re-deriving via `get_record_cid` only as the "simplest" option. The current code collects neither the op cid nor a combined read.
- **Location:** `crates/pds/src/read_after_write/mod.rs:122-140`.
- **Impact:** Two tree lookups where one suffices; on a burst of unindexed writes this doubles MST reads per record. Not a correctness bug (both reads hit the same opened repo), but wasteful on the hot read-after-write path.
- **Fix:** Either derive the CID from the value read once, or (preferred per plan) keep the op `cid` alongside the per-key time when populating `touched`, and skip the second lookup. If you keep `get_record_cid`, note the `Ok(None)` arm at line 135 is effectively dead (a value that just read as `Some` at line 123 will have a CID), so it is defensive-only.
