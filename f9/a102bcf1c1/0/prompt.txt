## Critical Issues (count: 1)

- **Issue**: `recordWithMedia#view` is built with a malformed `record` field. `hydrate_record_embed` returns the full `app.bsky.embed.record#view` object `{ "$type": "...record#view", "record": &lt;viewRecord|viewNotFound&gt; }`. But `hydrate_record_with_media_embed` then assigns `"record": record_view.get("record")` — pulling out only the **inner** `#viewRecord`/`#viewNotFound` and dropping the `record#view` wrapper.
- **Location**: `crates/pds/src/read_after_write/viewer.rs:249-253` (specifically line 251).
- **Impact**: The `app.bsky.embed.recordWithMedia#view.record` field is required by the lexicon to be a full `app.bsky.embed.record#view`. The Bluesky reference (`viewer.ts`) assigns the whole `formatRecordEmbed(...)` result there. The client expects `embed.record.record.&lt;viewRecord&gt;` nesting; this produces `embed.record.&lt;viewRecord&gt;` — a wrong shape that silently breaks quote-with-media rendering. This is exactly the "wrong field name/shape silently breaks the client" failure the plan called out for AC6.2.
- **Fix**: Assign the full record view: `"record": record_view` (not `record_view.get("record")`). Then add a test that hydrates an `app.bsky.embed.recordWithMedia` post and asserts `embed["$type"] == "...recordWithMedia#view"`, `embed["record"]["$type"] == "...record#view"`, and `embed["record"]["record"]["$type"] == "...#viewRecord"`.

## Important Issues (count: 2)

- **Issue**: AC6.2's HTTP path (`hydrate_quotes`) is entirely untested. The two record-embed tests drive `hydrate_record_embed` with a **hand-built** `QuoteMap`; nothing exercises `hydrate_quotes` itself — getPosts URL construction, `uris` query building, service-auth mint, JSON→`QuoteMap` parsing, or the empty-map-on-failure degradation. The plan's AC6.2 Testing block explicitly requires "mock AppView getPosts returning the quoted post" and "mock getPosts returning 5xx".
- **Location**: `crates/pds/src/read_after_write/viewer.rs:256-330` (no test coverage).
- **Impact**: The observable behavior of the one AppView call this phase adds is unverified. `wiremock::MockServer` is already used across the pds test suite (e.g. `routes/service_proxy.rs:393`) and `test_state` exposes a mutable `state.config.appview.url`, so this is achievable — not a tooling limitation. A regression in URL/auth/parse would ship silently.
- **Fix**: Add two tests: (1) point `state.config.appview.url` at a `MockServer` returning a getPosts body with `posts[]`, call `hydrate_quotes`, assert the URI maps to a populated `#viewRecord` through `post_view`; (2) mock a 5xx and assert an empty `QuoteMap` → embed degrades to `#viewNotFound` and the post still renders.

- **Issue**: `uris` query values are not URL-encoded. `hydrate_quotes` builds `format!("uris={}", uri_list.join("&amp;uris="))` from raw AT-URIs (`at://did:plc:.../app.bsky.feed.post/rkey`), which contain reserved `:` and `/`. Reqwest does not encode a hand-formatted URL string.
- **Location**: `crates/pds/src/read_after_write/viewer.rs:273-274, 288`.
- **Impact**: Latent correctness/interop risk — an unencoded reserved char in a query value is not guaranteed to round-trip through the AppView. The codebase already uses `urlencoding::encode` for exactly this (`routes/resolve_identity.rs:131`). A failed/garbled request degrades to `#viewNotFound` silently (no user-facing error), which masks the bug.
- **Fix**: Percent-encode each URI, or use reqwest's `.query(&amp;[("uris", uri)...])` builder which encodes automatically. The mock test above would surface this if the mock matches on the exact query string.
