<issue identifier="MM-472">
<title>blob_gc destroys the blobs of any account whose reconcile fails</title>
<description>
## Summary

`run_blob_gc`'s sweep phase is not gated on whether an account's reconcile succeeded in the same pass. When `reconcile_account` errors, that account's blobs are never pinned permanent, and the **global** sweep then deletes them once their upload grace expires — ownership row, physical `blobs` row, and the file on disk.

This is silent, irreversible data loss. It fires for any account whose repo walk errors, for any reason.

## Confirmed in production, 2026-07-25

`did:web:malpercio.dev` on `custos-obsign` lost **534 blobs**. Account created `01:51:43Z`; `blobs.temp_ttl_secs` defaults to 6h.

```
05:58:52Z  blob GC pass complete reconciled=0 released=0 expired=0   deleted=0   errors=1
06:28:52Z  blob GC pass complete reconciled=0 released=0 expired=0   deleted=0   errors=1
06:58:52Z  blob GC pass complete reconciled=0 released=0 expired=0   deleted=0   errors=1
07:28:52Z  blob GC pass complete reconciled=0 released=0 expired=0   deleted=0   errors=1
07:58:55Z  blob GC pass complete reconciled=0 released=0 expired=534 deleted=534 errors=1
08:03:48Z+ blob mirror: deleted bucket object with no blob row cid=... (x534)
```

`01:51 + 6h = 07:51`; the `07:28` pass was inside the window, the `07:58` pass was past it. `errors=1` was present on every pass for ~6 hours beforehand — the warning was visible the entire time and nothing escalated. The pass still logged "complete" and swept anyway.

The `blob_mirror` sweep then faithfully propagated the row deletions to the bucket, destroying the off-volume copy too. Recovery was only possible because the wallet's iCloud media backup existed.

## Mechanism

1. `uploadBlob` stamps every new `blob_owners` row with `temp_until = now + blobs.temp_ttl_secs` (default 6h) — `crates/pds/src/routes/upload_blob.rs`.
2. Only `blob_gc`'s reconcile clears `temp_until` (pins permanent), by walking the MST — `reconcile_account` in `crates/pds/src/blob_gc.rs`.
3. `reconcile_account` calls `collect_referenced_blob_cids` first and propagates with `?`. On error **neither** the pin loop nor the release loop runs — hence `reconciled=0` on every pass above.
4. Phase 2 calls `blobs::list_expired_temp_owners`, which scans **all** accounts (`WHERE temp_until IS NOT NULL AND temp_until < datetime('now') AND ref_count = 0`) with no reference to which accounts reconciled successfully.
5. Grace expires → sweep deletes. Last owner gone → physical row + file deleted.

## Proposed fix

Collect the set of DIDs whose reconcile errored this pass and exclude them from the sweep. Fail closed: an account whose references we could not compute must never have its blobs collected. A permanently-failing account then leaks disk until the underlying fault is fixed, which is strictly the right trade against irreversible deletion.

Secondary: a pass with `errors > 0` should not present as a clean "pass complete" — consider recording it distinctly in `sweep_status` / metrics so an operator has something to alert on. See the observability issue.

## Regression test

Reconcile fails for account A (repo walk error), A has an expired-grace unreferenced blob, a healthy account B has one too. Assert A's blob survives the pass and B's is collected.

## Mitigation applied to the affected account

```sql
UPDATE blob_owners SET temp_until = NULL WHERE account_did = 'did:web:malpercio.dev';
```

Safe because the sweep requires `temp_until IS NOT NULL`, and reconcile errors before reaching the release loop, so nothing re-arms the clock. This is a stopgap on one account, not a fix.
